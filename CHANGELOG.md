# Журнал змін

Усі помітні зміни в цьому проекті документуються тут.

Формат базується на [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
проект дотримується [Семантичного версіонування](https://semver.org/spec/v2.0.0.html).

## [1.4.0] — 2026-09-01

> **Розмір бази суттєво зросте.** `inetnum` — найчисленніший тип об'єктів у RIPE DB (мільйони записів проти сотень тисяч `route`). Після першого `--get-data` очікуйте зростання приблизно втричі.
>
> **Оновлення схеми.** Додається таблиця `rpsl_net` з індексами `idx_rpsl_net_exact` та `idx_rpsl_net_range`. Міграція автоматична, але наповнюється таблиця лише під час наступного `--get-data` — до того нові опції нічого не знайдуть.

### Додано
- `inetnum` та `inet6num` до типів об'єктів, що зберігаються з `ripe.db`
- `--retrieve-route` / `-rr`, `--retrieve-route6` / `-rr6`, `--retrieve-inetnum` / `-rin`, `--retrieve-inet6num` / `-ri6n`. Аргументом може бути **будь-яка адреса чи префікс усередині** об'єкта, не лише його точне значення: `-ri6n 2a04:42c1:3:c::3/64` знайде і `2a04:42c1::/32`, і зовнішній `2a04:42c0::/29`. Результати виводяться від найменш специфічного до найбільш специфічного
- До кожного знайденого об'єкта виводиться його `organisation` за посиланням `org:`; для `inetnum` та `inet6num` — додатково `route`/`route6` об'єкти, що лежать усередині
- Таблиця `rpsl_net` з числовими межами діапазонів адресних RPSL-об'єктів. `inetnum` зберігається у вигляді діапазону (`192.0.2.0 - 192.0.2.255`), який не завжди зводиться до одного префікса, тож розкладається на точний набір CIDR-блоків — кожен окремим рядком, що вказує на той самий об'єкт

### Технічна примітка
Ці об'єкти сильно перекриваються — `/29` і вкладений у нього `/48` існують одночасно, — тому прийом «найближчий знизу + `LIMIT 1`», застосований до розподілів RIR, тут не працює, а предикат `firstip <= ? AND lastip >= ?` вироджується у сканування значної частини таблиці. Замість цього зберігається довжина маски, а адреса запиту маскується до кожної можливої довжини й шукається точним збігом. Заміряно на 268 тис. рядків: **2 мс проти 424 мс** на 20 пошуків, і розрив зростатиме з обсягом `inetnum`.

## [1.3.0] — 2026-08-21

> **Перейменування класів.** Класи переведено на `PascalCase` згідно з конвенцією Java (`parseRpsl` → `ParseRpsl`, `retrieveAutNum` → `RetrieveAutNum` тощо). Публічного API проєкт не має, CLI не змінився — але зовнішні патчі проти старих імен доведеться переписати.
>
> **Оновлення схеми.** Додаються покривні індекси `idx_ipv4_range` / `idx_ipv6_range`, знімаються `idx_ipv4_firstip`, `idx_ipv4_lastip`, `idx_ipv6_firstip`, `idx_ipv6_lastip`. Міграція автоматична; місце повертає `--vacuum`.

### Виправлено
- Діапазони IPv4, розмір яких не є степенем двійки, зберігалися невірно: префікс обчислювався як `32 - floor(log2(count))`, тож делегування на 1536 адрес ставало одним `/22` (1024 адреси) — решта діапазону просто зникала з бази. Тепер діапазон розкладається на точний набір CIDR-блоків через бібліотеку `ipaddress` (1536 → `/24 + /23 + /23 + /24`), а `ipv4ToCidr` використовує цілочисельну арифметику й відхиляє нестепені двійки замість тихого округлення
- Дані втрачалися назавжди після часткової помилки: `store()` ковтав порядкові помилки, цикл читання завершувався нормально, і `file_metadata` оновлювався. Наступний запуск бачив «файл не змінився» й пропускав завантаження. Додано лічильник помилок на файл; за наявності втрат метадані не записуються, і файл перезавантажується наступного разу
- Кожне невдале завантаження лишало файл у `/tmp`: тимчасовий файл створювався до HTTP-запиту й не видалявся при помилці. Створення перенесено після перевірки відповіді, видалення — в обробник помилки
- Нечисловий аргумент AS давав сирий `NumberFormatException` у стектрейсі; тепер це зрозуміле повідомлення
- Незакриті ресурси: десять `createStatement()` і близько двадцяти `ResultSet` переведено на try-with-resources

### Змінено
- `--retrieve-route-origin`, `--retrieve-mnt-by`, `--retrieve-mntner` і `--retrieve-network-origin` відкривали **нове з'єднання з БД на кожен рядок** результату — для AS із 500 маршрутами це 500 відкриттів файлу. Замінено одним `JOIN` на з'єднання
- Пошук мережі за IP більше не сканує половину таблиці: замість `firstip <= ? AND lastip >= ?` (план — `SEARCH ipv4 USING INDEX idx_ipv4_lastip`) виконується пошук найближчого знизу з `LIMIT 1` по покривному індексу `(firstip, lastip, network)`. Розподіли RIR не перетинаються, тож верхню межу достатньо перевірити в Java
- `ParseExtended` готував і закривав чотири `PreparedStatement` на кожен рядок extended-файлу, а «батч» завжди складався з одного рядка. Statement-и готуються один раз на файл, записи накопичуються батчами по 1000
- UPDATE у RPSL виконувався по одному рядку, поки INSERT батчився; тепер батчиться разом з рештою
- `blockCache` був `Map<String, String>` і зберігав лише останнє значення на тип ключа, тобто ловив дублікат тільки в сусідніх блоках, хоча виглядав як повна дедуплікація. Розділено на `seenKeyTypes` (те, що справді потрібно для `cleanupOutdatedRpsl`) і явну перевірку сусіднього блоку

### Безпека
- Завантаження дозволено лише за схемою `https` (звичайний `http` — тільки на localhost, для тестового дзеркала). Дані з дзеркала стають відповіддю на питання «чия це мережа», тож не мають піддаватися підміні в дорозі
- Додано обмеження на обсяг завантаження (8 ГіБ) та розпакування (64 ГіБ). `Content-Length` тепер перевіряється, а розпакований потік обгорнуто лічильником, який припиняє читання за межею — інакше зламане чи скомпрометоване дзеркало могло заповнити `/tmp` або нескінченно роздувати базу
- `--search-rpsl-object` отримав обмеження загального часу пошуку (120 с) із зрозумілим повідомленням замість видимого зависання. Посимвольний бюджет кроків не використано свідомо: він коштує ~44% на кожному пошуку, а класичні катастрофічні патерни (`(a+)+$`, `(x+x+)+y`, `^(a+)+$`) на рушії JDK 21 відпрацьовують за одиниці мілісекунд — платити стільки на основному шляху за невідтворену загрозу недоречно
- `Config.printedBlockHashes` переведено на `ConcurrentHashMap.newKeySet()`

## [1.2.0] — 2026-08-21

> **Оновлення схеми.** До таблиці `rpsl` додається колонка `block_sha512`. Міграція виконується автоматично при першому запуску — видаляти чи перестворювати базу не потрібно. Разово виконається заповнення хешів для наявних записів; для бази ~1 ГБ це помітна пауза, яка більше не повториться.

### Виправлено
- Останній неповний батч RPSL (до 999 об'єктів) губився на кожному запуску: фінальний скид було прив'язано до умови «лишився незбережений блок», але дампи RPSL закінчуються порожнім рядком, тому останній блок уже зберігав `initBeginBlock()`, умова не виконувалася, і накопичені батчі `rpsl` та `temp_rpsl` відкидалися при закритті statement-ів. Через відсутність записів у `temp_rpsl` метод `cleanupOutdatedRpsl` додатково вважав ці об'єкти застарілими й видаляв їх. Скид зроблено безумовним
- `parseGeolocations` губив до 999 геозаписів на файл: один лічильник `batchCount` обслуговував два незалежні statement-и, тож при досягненні межі скидався лише один із них, а лічильник обнулявся; накопичене другим лишалося в черзі, і якщо останній скид припадав рівно на межу, фінальна умова `if (batchCount > 0)` не спрацьовувала. Лічильники розділено на `updateBatchCount` та `insertBatchCount`, фінальний скид виконується безумовно для обох
- NPE при неповному `whoislitelocal.properties`: перевірка на порожнечу застосовувалася до `paramUrls` — назви ключа, яка приходить літералом і ніколи не буває порожньою, — замість значення властивості. Відсутній ключ давав `NullPointerException` у `props.getProperty(...).split(",")`. Читання винесено в `readUrls()`, який перевіряє саме значення й повертає порожній масив
- `PRAGMA auto_vacuum = INCREMENTAL` не діяв: виконувався після `setAutoCommit(false)`, тобто всередині транзакції, де SQLite його ігнорує. Через це `PRAGMA incremental_vacuum` на такій базі нічого не робив. Pragma перенесено на етап до транзакції; фактичний режим перевіряється й логується
- `--vacuum` не вмикав `auto_vacuum` на наявній базі: режим змінюється лише коли `VACUUM` перебудовує файл на тому самому з'єднанні, де задано pragma, а `executeVacuum()` відкривав власне з'єднання без неї. Pragma додано перед `VACUUM`
- Збірка не працювала на JDK 21–23: прапор `-J--sun-misc-unsafe-memory-access=allow` передавався форкнутому компілятору безумовно, хоча існує лише з JDK 24. Винесено в профіль з активацією `<jdk>[24,)</jdk>` — проєкт знову збирається на будь-якому JDK від 21

### Змінено
- Перевірка змін RPSL більше не хешує блок у SQL: запит `SELECT sha512(block) ... ` змушував SQLite читати повний текст кожного блоку з диска й проганяти через Java-UDF, після чого той самий блок хешувався ще раз уже в Java. Хеш тепер зберігається в колонці `rpsl.block_sha512` і обчислюється один раз під час запису; перевірка стала пошуком по індексу без читання тексту блоку
- Прибрано індекс `idx_rpsl_kv` — точний дублікат автоіндексу від `UNIQUE(key, value)`, який планувальник і так не використовував. Наявні бази втрачають його автоматично; місце повертається після `--vacuum`
- SHA-512 форматується через `HexFormat.of().formatHex()` замість `String.format("%02x")` у циклі по 64 байтах

## [1.1.5] — 2026-07-15

### Додано
- `--search-rpsl-object` / `-sro` `<pattern>`: повнотекстовий пошук по RPSL-об'єктах за шаблоном або регулярним виразом (case-insensitive). Шукає по полю `name` в таблиці `asn` та по всьому блоку в таблиці `rpsl`. Для кожного результату виводить ідентифікаційний рядок об'єкта (перший рядок блоку) та лише ті рядки, у яких є збіг із шаблоном. Regex-підтримка реалізована через UDF `REGEXP`, зареєстровану через `org.sqlite.Function` (sqlite-jdbc); патерн компілюється один раз і перевикористовується для всіх рядків

## [1.1.0] — 2026-07-15

### Додано
- Паралельне завантаження HTTP у межах кожної групи URL за допомогою virtual threads: усі файли, що потребують оновлення, завантажуються одночасно
- Паралельне виконання незалежних парсерів (`parseExtended`, `parseAsnames`, `parseGeolocations`) в `executeGetData`; вони записують у різні таблиці. `parseRpsl` виконується після них послідовно
- SQLite WAL-режим (`PRAGMA journal_mode = WAL`) для кращої паралельної роботи з читанням/записом
- `PRAGMA busy_timeout = 30000` на кожному з'єднанні для коректного очікування при конкуренції за запис
- Lombok `@Slf4j` замість ручних полів `Logger` у всіх класах; кожен клас тепер логує під власним ім'ям
- `CONTRIBUTING.md` із описом збірки, конфігурації та гілкової стратегії

### Виправлено
- `cleanupOutdatedRpsl` видаляв усі незмінені RPSL-записи при кожному інкрементальному оновленні: `saveBlock()` повертався раніше, не вставляючи незмінені блоки в `temp_rpsl`, тому предикат `NOT EXISTS` вважав кожен незмінений об'єкт застарілим
- `processFiles` завантажував `whoislitelocal.properties` з файлової системи за відносним шляхом, що робило JAR залежним від поточної директорії; перейшло на завантаження з classpath через `getResourceAsStream()`

### Змінено
- Поріг VACUUM змінено з абсолютного (100 сторінок) на відносний (25% фрагментації)
- Дедублікація виводу: `Config.printBlock()` дедублює на рівні блоків (SHA-512 Highlander) та на рівні атрибутів всередині блоку з урахуванням continuation-рядків (RFC 2622 §2)
- Continuation-рядки RPSL тепер зберігаються через `stripTrailing()` замість `trim()`
